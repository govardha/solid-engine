The Big Picture

Why Do We Need a Layered Model?

Two engineers built the internet: Vint Cerf and Bob Kahn, 1974. The core insight: separate concerns. A web developer shouldn't need to know how Ethernet checksums work. A network driver shouldn't care about HTTP headers.

Layers enforce contracts. Each layer talks only to the layer above and below. You can replace Ethernet with Wi-Fi, HTTP with gRPC — and the other layers don't care.

Analogy: Shipping a package. You write the letter (application). Stuff it in an envelope (transport). Stick on an address (network). Drop at FedEx (link). You don't care how FedEx routes it.
L7 Application What apps speak HTTP SSH DNS
L6 Presentation Encoding, TLS TLS
L5 Session Session state Sockets
L4 Transport End-to-end delivery TCP UDP
L3 Network Addressing & routing IP ICMP
L2 Data Link Node to node Ethernet ARP
L1 Physical Bits on wire Copper · Fiber · RF
We live at L3 and L4 today. L7 is where your code runs. L3/L4 is where the OS routes, filters, and delivers traffic. This is the layer that iptables, firewalls, load balancers, and network engineers all operate on.
Teach the OSI model but frame it practically: L1–L2 is the NIC driver's problem. L3–L4 is the OS kernel's problem. L5–L7 is your application's problem. Today we're in kernel territory.
Pro tip: Run ip addr show and ip route show on a terminal and ask "which layer is this?" IP addresses = L3. MAC addresses = L2. That's the first test.
Layer 3 — Network

IP Addresses: How Machines Are Named on a Network

IPv4 — 32 bits, 4 octets

192.168.1.47 ↑ ↑ ↑ ↑ Network portion Host portion (subnet dependent)

Every device on a network gets an IP address. The subnet mask (e.g. /24 = 255.255.255.0) determines which bits are "network" vs "host". Machines in the same subnet talk directly. Different subnets require a router.

# Show your IPs ip addr show ip -4 addr show eth0 # Show routing table ip route show
CIDR notation: 10.0.0.0/16 means first 16 bits are network. Gives you 65,534 usable hosts. /24 gives 254. /32 is a single host.

ICMP — The Network's Diagnostic Tool

# Reachability test ping -c 4 8.8.8.8 # Path tracing — see every hop traceroute 8.8.8.8 # or on RHEL8: mtr 8.8.8.8
ICMP is not TCP or UDP — it's L3 only. ping/traceroute responses being blocked ≠ the host is down. Firewalls commonly block ICMP. A closed TCP port will still reply.
Demo: ip addr show to see the machine's IP. Then ping 8.8.8.8. Then ping -c 1 192.168.1.1 (default gateway). Ask: why does one work over the network and one stays local?
Gotcha to plant: "If two machines are on different subnets, what must exist between them?" Answer: a router (or a default gateway). That's the next question.
Layer 3 — Addressing

Private Addresses & NAT: How 4 Billion IPs Serve 8 Billion People

RFC 1918 — The Three Private Blocks

IPv4 is 32 bits = ~4.3 billion addresses. The internet has more devices than that. The fix: reserve blocks that ISP backbone routers will never forward. Reuse them freely behind NAT.

BlockRangeSizeTypical Use
10.0.0.0/8 10.x.x.x 16.7M Cloud VPCs, enterprise, Kubernetes. Your OCI VCN is 10.0.0.0/16.
172.16.0.0/12 172.16–31.x.x 1M Docker default bridge (172.17.0.0/16). Your Pi-hole container lives here.
192.168.0.0/16 192.168.x.x 65K Home routers (TP-Link, cable modems). Everyone's LAN.
Non-routable means: if a packet with dst 10.x.x.x or 192.168.x.x hits an ISP core router, it's dropped. Two different homes can both run 192.168.1.1 with zero conflict — they never meet on the public internet.

NAT — The Mechanism That Makes It Work

NAT (Network Address Translation) sits at the boundary between private and public. Your home router, your OCI IGW path, vpn7 for WireGuard clients — all doing NAT.

Your laptop (192.168.1.5) sends packet to 8.8.8.8:53 Router intercepts — rewrites src: 192.168.1.5:54321 → 203.0.113.5:54321 Logs mapping in conntrack table Reply arrives at 203.0.113.5:54321 Router looks up conntrack → 192.168.1.5 Rewrites dst back, delivers to laptop
SNAT vs DNAT:
SNAT (outbound) — rewrites source IP. Your home router. vpn7's MASQUERADE rule for WireGuard clients. Initiated from inside.
DNAT (inbound) — rewrites destination IP. Port forwarding. How inbound :500 reaches vpn7's WireGuard process. Requires an explicit rule — no prior connection means no conntrack entry.
# View the kernel's NAT conntrack table sudo conntrack -L 2>/dev/null | head -10 # or raw: cat /proc/net/nf_conntrack | head -5 # vpn7's MASQUERADE rule (WireGuard clients) sudo iptables -t nat -L POSTROUTING -v -n
Hook to open with: Ask them — "your phone is 192.168.x.x at home. What IP does google.com see when you visit it?" Run curl ifconfig.me from their laptop. The answer IS the NAT gateway. That gap between what they have and what the internet sees is NAT.
vpn7 context: vpn7 is in a public OCI subnet (10.0.0.0/16 VCN, direct IGW route). It has a real public IP. When WireGuard peers connect and their tunnel traffic needs to reach the internet, vpn7 runs iptables MASQUERADE — it's acting as their NAT gateway, same as their home TP-Link does for them. Docker containers (172.17.0.0/16) get the same treatment automatically.
CGNAT gotcha: Many mobile ISPs do carrier-grade NAT (RFC 6598, 100.64.0.0/10) — your phone behind mobile data may be double-NATted. That's why some VPNs and P2P break on cellular.
Layer 4 — Transport

TCP: Reliable, Ordered, Connection-Oriented

TCP is the postal service that guarantees delivery, tracks every package, and re-sends anything lost. It's the contract between two endpoints.

What TCP Guarantees

1
Delivery confirmation
Every byte sent gets an ACK back. If ACK doesn't arrive, TCP retransmits. Automatically.
2
Ordering
Packets arrive out of order on the wire — TCP reassembles them in the correct sequence using sequence numbers.
3
Flow control
Receiver tells sender "I can only handle X bytes right now" via the window size field. Prevents buffer overflow.
4
Congestion control
TCP detects packet loss and slows itself down. This is why large downloads back off when the network is saturated.

TCP Header Anatomy

Src Port (16b)
Dst Port (16b)
Sequence Number (32 bits)
Acknowledgement Number (32 bits)
Hdr Len
Flags: SYN ACK FIN RST PSH URG
Window Size
Checksum
Urgent Pointer
Options (variable) + Data
The flags are everything. SYN starts a connection. ACK acknowledges. FIN closes gracefully. RST kills immediately. You'll see all of these in Wireshark.
Key concept to drive home: TCP adds overhead — that 20-byte minimum header on every segment, plus the round-trips for handshake and ACKs. That overhead is the cost of reliability.
Demo setup: tcpdump -i eth0 -n port 443 while hitting any HTTPS site. Watch the SYN → SYN-ACK → ACK sequence in real time.
TCP Deep Dive

The 3-Way Handshake: How TCP Connections Are Born

Before a single byte of HTTP or application data flows, TCP performs a synchronized state negotiation. This is the "conversation before the conversation."

1
SYN — "I want to connect"
Client sends SYN with its Initial Sequence Number (ISN). Randomly chosen to prevent spoofing. "My sequence starts at 1234."
2
SYN-ACK — "OK, and here's mine"
Server ACKs client's ISN (seq+1) and sends its own ISN. "Got your 1234, mine starts at 5678."
3
ACK — "Connection established"
Client ACKs server's ISN. Both sides now have synchronized sequence numbers. Data flows.
Why 3 and not 2? 2-way only confirms one direction. A 3-way handshake proves both directions work — client→server AND server→client. You need both for full-duplex TCP.

ASCII Timeline

Client Server | | |------- SYN (seq=x) ----->| | | [Server: LISTEN → SYN_RCVD] |<-- SYN-ACK (seq=y,ack=x+1)--| | | |------- ACK (ack=y+1) --->| | | [Both: ESTABLISHED] |====== DATA FLOWS ========| | | |------- FIN ------------->| [Client: FIN_WAIT_1] |<------ ACK --------------| |<------ FIN --------------| [Server: CLOSE_WAIT] |------- ACK ------------->| [TIME_WAIT → CLOSED]
SYN Flood Attack

Attacker sends millions of SYNs, never completes the handshake. Server fills SYN queue, runs out of memory for legitimate connections. Defense: SYN cookies.

# Watch TCP states live ss -tn # See SYN_RECV, ESTABLISHED, # TIME_WAIT, CLOSE_WAIT netstat -an | grep -E 'SYN|ESTAB'
Best demo: ss -tn state established while loading a web page. Watch connections appear and disappear. Ask them: "what happens if step 2 never arrives?" Answer: SYN timeout, client retries with exponential backoff.
TCP TIME_WAIT question: Why does TIME_WAIT exist? Answer: ensures the final ACK reached the server. Lasts 2*MSL (Maximum Segment Lifetime, typically 60s). You'll see this constantly on busy servers.
Layer 4 — Transport

UDP: Fire and Forget — When Speed Beats Certainty

UDP is the postcard — no tracking, no confirmation, no retransmit. What it trades in reliability, it wins back in raw speed and zero connection overhead.

UDP Header — Brutally Simple

Src Port (16 bits)
Dst Port (16 bits)
Length (16 bits)
Checksum (16 bits)
Data

TCP header: minimum 20 bytes. UDP header: always 8 bytes. No handshake. No state. No ACK. You send, you hope.

No connection = no overhead. UDP datagrams are sent immediately. The kernel doesn't maintain any connection table for UDP sockets. This matters massively at scale — DNS servers handle millions of queries/sec using UDP.

UDP Is Not "Worse Than TCP" — It's Different

ProtocolReliabilityOverheadUse Case
TCP Guaranteed High HTTP, SSH, DB, email
UDP Best-effort Minimal DNS, video, gaming, VoIP

Real Applications Using UDP

DNS :53

Query fits in one packet. Falls back to TCP only if response > 512 bytes (now 4096 with EDNS)

Video Streaming

A dropped frame is better than a paused video. Stale data is useless — don't retransmit it.

WireGuard / QUIC

VPN tunnels and HTTP/3 both run over UDP. They implement their own reliability layer on top.

NTP :123

Time sync. You don't need guaranteed delivery for "what time is it?" — fast wins.

Key insight to give them: WireGuard (which they'll use) runs over UDP port 51820. QUIC (HTTP/3) runs over UDP port 443. Modern protocols are moving TO UDP and implementing reliability in userspace because they can tune it better than the kernel's TCP stack.
Demo: dig google.com — that's UDP. dig +tcp google.com — forces TCP. Compare the timing. DNS over UDP is measurably faster.
Ports & Sockets

Ports: How the OS Routes Packets to the Right Process

An IP address gets you to a machine. A port gets you to a process. Together, they form a socket — the unique 5-tuple that identifies every active connection.

Socket = {Protocol, Src IP, Src Port, Dst IP, Dst Port} Example: TCP 10.0.1.5:54321 → 93.184.216.34:443 That 5-tuple is UNIQUE. The kernel uses it to demux packets to the right process.
Port ranges:
0–1023 → Well-known / privileged (needs root to bind)
1024–49151 → Registered / common apps
49152–65535 → Ephemeral (kernel-assigned for outbound)
# What's listening on this machine? ss -tlnp # All active connections ss -tnp # Who owns port 8080? lsof -i :8080

Putting It Together

What Happens When You Run: curl https://github.com

1
DNS Resolution (UDP :53)
OS checks /etc/hosts, then /etc/resolv.conf resolver. Sends UDP query for github.com A record. Gets back 140.82.121.3 (or similar). All in ~5ms.
2
Routing Decision (L3)
Kernel checks ip route table. 140.82.x.x is not local, so: use default gateway (your router). ARP resolves the gateway MAC address on L2.
3
TCP Handshake to :443 (SYN → SYN-ACK → ACK)
Kernel picks ephemeral port (e.g. 54812). Sends SYN. GitHub's LB responds SYN-ACK. Connection ESTABLISHED.
4
TLS Handshake (L5-L6)
Client Hello → Server Hello + Certificate → Key exchange → Finished. Now all data is encrypted. TLS sits on TOP of TCP — it's not replacing it.
5
HTTP GET (L7)
curl sends GET / HTTP/1.1. GitHub's server responds with 301 redirect or 200 OK + HTML. All riding inside the established TCP+TLS session.
6
TCP Teardown (FIN/ACK)
curl sends FIN. Server ACKs + sends its own FIN. Client ACKs. Connection enters TIME_WAIT, then CLOSED. Socket resources freed.
Every single step above is visible in Wireshark or tcpdump. The wire doesn't lie. When something breaks, this is the chain you debug — start at L3 (can I ping it?), then L4 (can I TCP connect?), then L7 (is the app responding?).
# See all layers live tcpdump -i eth0 -n host github.com # Measure each step curl -w "\nDNS: %{time_namelookup}s\nConnect: %{time_connect}s\nTLS: %{time_appconnect}s\nTotal: %{time_total}s\n" -o /dev/null -s https://github.com
This is the money slide. Everything from the previous slides converges here. Walk it step by step and pause at each one to point back: "remember SYN-ACK from slide 5? That's step 3."
Best live demo: The curl -w timing breakdown shows every layer's contribution. DNS lookup, TCP connect time, TLS time are all distinct. Run it against github.com and a local service — compare the numbers.
TCP Internals

TCP State Machine: What the Kernel Tracks per Connection

TCP is a state machine. Every connection the kernel maintains has a state. These states are visible with ss and netstat. When debugging production issues, these states tell the story.

StateMeaning
LISTENServer socket waiting for SYN. Your nginx/postgres are here.
SYN_SENTClient sent SYN, waiting for SYN-ACK.
SYN_RCVDServer got SYN, sent SYN-ACK, waiting for ACK.
ESTABLISHEDConnection active. Data flows.
FIN_WAIT_1/2Active close — sent FIN, draining.
CLOSE_WAITGot FIN from peer, app hasn't called close() yet. Bug indicator.
TIME_WAITClosed but holding 2*MSL (~60s) to catch stale packets.
CLOSEDConnection fully terminated.

Prod Debugging Cheatsheet

# Count connections by state ss -tn | awk '{print $1}' | sort | uniq -c | sort -rn # Lots of TIME_WAIT = high connection churn # → use HTTP keep-alive / connection pooling # Lots of CLOSE_WAIT = app bug # → app not calling close() after receiving FIN # SYN_RECV flooding = SYN flood attack # → check: sysctl net.ipv4.tcp_syncookies # Ports exhausted? (ephemeral range full) cat /proc/sys/net/ipv4/ip_local_port_range # Default: 32768 to 60999 = ~28k ports # Fix: tune or use SO_REUSEPORT
CLOSE_WAIT ≠ TIME_WAIT. TIME_WAIT is normal and healthy — the OS is being careful. CLOSE_WAIT accumulating means your application has a resource leak — it received a FIN but the app never closed the socket. That will exhaust file descriptors.
# See per-process socket usage ss -tnp | grep CLOSE_WAIT | awk '{print $NF}' | sort | uniq -c
Production context: In a real environment you'll frequently see thousands of TIME_WAIT entries on a busy web server — that's normal. What kills you is CLOSE_WAIT accumulating. The fix is always in the application code, not the kernel tunables.
RHEL8 note: ss is the modern replacement for netstat. On RHEL8, netstat may not even be installed by default (it's in the net-tools package). Teach ss.

Quick Diagnostic Patterns

# Can I reach the host at all? (L3) ping -c 3 # Can I open a TCP connection? (L4) nc -zv # or: timeout 3 bash -c 'cat < /dev/null > /dev/tcp/host/port' # What is the app saying? (L7) curl -v https://host:port/path # Who is listening locally? ss -tlnp # Follow a packet from this machine tcpdump -i any -n host -w /tmp/cap.pcap # Open in wireshark for GUI analysis
Debug order:
1. ping → L3 reachability
2. nc -zv → L4 port open?
3. curl -v → L7 app responding?
4. tcpdump → what's actually on the wire?
This sequence eliminates 90% of "why can't I connect" issues in under 2 minutes.
Lab exercise: Give them a host that has a firewall rule blocking port 80 but not 22. Have them diagnose which layer the problem is at. They should:
1. ping succeeds (L3 OK)
2. nc -zv host 80 fails (L4 blocked)
3. nc -zv host 22 succeeds (SSH open)
Then they check iptables rules. This is the debugging loop they'll run for the rest of their careers.
Bridge Forward

How This Connects to Everything Else You'll Learn

Everything in modern infrastructure is just TCP/IP with extra labels on it. Now that you have the foundation:

DNS (Next Session)

DNS queries are UDP port 53. Responses >512 bytes fall back to TCP :53. When you debug DNS, you're debugging UDP datagrams. You already know the plumbing.

iptables / nftables

Firewall rules match on the 5-tuple: src IP, dst IP, protocol, src port, dst port. Every ACCEPT and DROP rule is operating on exactly what you learned today.

Docker Networking

Docker creates virtual network interfaces, assigns private IPs (172.17.0.0/16), and uses NAT + port forwarding to map container ports to host ports. All L3/L4.

WireGuard / Tailscale

WireGuard is UDP packets containing encrypted IP packets. Tailscale is WireGuard + a coordination plane. It's just IP over UDP — the model you now understand.

TLS / HTTPS

TLS rides on top of an established TCP connection. The TCP handshake you just learned always happens first, then TLS negotiates on top of it. They're sequential, not parallel.

Load Balancers / AWS ALB

An ALB terminates your TCP (and TLS) connection, then opens a new TCP connection to a backend instance. It's a TCP proxy — SYN flood mitigation happens here.

The through-line: Every session from here on builds on L3 and L4. When things break, you'll always come back down to this layer to find the truth. The wire doesn't lie.
Closing move: Ask them to name one thing they use every day that they now understand differently. Likely answers: browser tabs (each = TCP connection), Slack (TCP to relay servers), SSH (TCP :22 with a multiplexed channel protocol on top).
Homework (if you want to assign it): Open Wireshark on their laptop, visit any website, find the SYN, SYN-ACK, ACK in the capture. Screenshot it. That's the assignment.
Check for Understanding

5 Questions That Test Real Understanding

Q1
You curl a service and get "connection refused." What does that actually mean at the TCP level?
Answer: The server received the SYN and replied with RST. IP routing worked (L3 OK), but nothing is listening on that port (L4 rejected). RST = "I'm here, but I'm not taking connections on this port."
Q2
Why does a DNS server use UDP instead of TCP?
Answer: A DNS query + response is typically <512 bytes — fits in one UDP datagram. No need for handshake. At millions of queries/sec, eliminating the 3-way handshake overhead is massive.
Q3
Two services on the same machine both listen on port 8080. What happens?
Answer: Second bind() fails with EADDRINUSE. A port can only be bound once per IP per protocol (unless SO_REUSEPORT is set). The kernel can't demux if two processes claim the same dst_port.
Q4
Your app has 50,000 CLOSE_WAIT connections. Production is degrading. What's wrong?
Answer: The application received FIN from the remote side but never called close() on the socket. It's a code bug — the app is leaking file descriptors. Kernel tunables won't fix it.
Q5
ping succeeds but nc -zv host 443 fails. What layer is the problem at, and what are your next steps?
Answer: L3 works (ICMP flows). L4 is blocked. Suspect: firewall rule dropping TCP :443 (check iptables -L, security group, or the destination service isn't running). tcpdump on both sides next.
Don't just reveal answers — make them work for it. For Q1, ask "what RST means" first. Most won't know. That's the lesson. For Q5, walk through the elimination — if they get to "check iptables", they've internalized the model.
